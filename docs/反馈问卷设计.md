# 反馈问卷（可直接录入问卷平台）

> **这份问卷是我替你设计的题目，不是问卷本身。**
> 你要做的：去腾讯问卷 / 问卷星 / 金数据，把下面 10 道题照着建一遍（约 5–10 分钟），
> 拿到分享链接，填进 `js/config.js` 的 `FEEDBACK_URL`。
>
> **为什么要你自己建**：问卷收集到的数据要写进你的报告，账号和归属必须是你的；
> 我也无法替你注册平台账号。

---

## 一、设计思路（写报告时可以直接用这段）

问卷刻意**不问**「你觉得好用吗」这类评价题 —— 同学出于客气会说好看，
这种数据写进报告没有说服力，评委也会质疑。

问卷只问两类东西：

1. **行为事实**：用了几天、录了几道题、有没有中途放弃、还会不会再用。
   行为无法客套，也和你从「导出使用数据」拿到的客观记录可交叉验证。
2. **具体卡点**：哪一步最麻烦、最想要什么。
   这一项是为了**改产品**，不是为了让报告好看。

10 道题、预计 2 分钟填完。超过 3 分钟完成率会明显下降。

## 二、问卷题目（照抄即可）

### 标题

**错题通使用反馈（约 2 分钟）**

### 说明文字（放在问卷开头）

> 这是我参加挑战杯做的错题本工具，想听听真实使用感受。
> 全部匿名，不会收集你的姓名学号，也看不到你录的题目。
> 没有标准答案，说缺点比说优点对我更有帮助。

---

### Q1【单选，必答】你大概用了几天？

- A. 只是打开看了看，没实际用
- B. 1–2 天
- C. 3–6 天
- D. 一周以上

> **报告用途**：真实留存率。「打开看了看」和「用了一周」是两种完全不同的结论，
> 必须分开统计，不能合并成「有 N 人使用」。

---

### Q2【单选，必答】这段时间你大概录了多少道错题？

- A. 0 道
- B. 1–5 道
- C. 6–15 道
- D. 16 道以上

> **报告用途**：与「导出使用数据」里的 `mistakeCount` 交叉验证。
> 若 Q2 说 16 道以上、导出数据只有 3 道，说明用户高估自己或导出不完整，要在报告里说明。

---

### Q3【单选，必答】你用过下面哪些功能？（多选改成多选，见下）

**改成【多选，必答】**：

- □ 录错题
- □ 错题本筛选
- □ 薄弱点诊断（看图表）
- □ 智能组卷练习
- □ 今日复习
- □ 打印练习卷
- □ 导出备份

> **报告用途**：「用了哪些功能」的分布，直接对应报告的功能使用表。
> 若「打印」几乎没人用，说明这个功能是伪需求（这也是有价值的发现）。

---

### Q4【单选，必答】哪一步最麻烦？

- A. 录入错题（打字、填知识点太费事）
- B. 选知识点（选项太多，找不到对应章节）
- C. 看诊断页（图表看不懂，不知道结论在说什么）
- D. 组卷和作答（流程太长）
- E. 其他（请写在第 9 题）

> **报告用途**：这是**最有行动价值**的一题，直接决定 D7 该优化什么。
> 如果多数人选 B，说明知识点粒度需要调整 —— 这正好是你让我核教材章节的理由。

---

### Q5【单选，必答】诊断页给出的掌握度和「数据不足」提示，你觉得说得准吗？

- A. 基本符合我的实际感觉
- B. 有的准有的不准
- C. 不太准
- D. 没看懂那个百分比和区间是什么意思

> **报告用途**：**这是整个问卷最关键的一题**。
> 你的核心创新点就是「贝叶斯掌握度 + 可信区间」，如果用户选 D（没看懂），
> 说明这个创新点在产品层面是失败的 —— 统计再正确，用户看不懂等于零。
> 报告里必须如实写，并说明你会怎么改（而不是掩盖）。

---

### Q6【单选，必答】「数据不足」这个提示，你当时的反应是？

- A. 理解，知道要多做几道题
- B. 有点困惑，不知道要做多少才够
- C. 觉得是 bug / 功能坏了
- D. 没注意到这个提示

> **报告用途**：检验「诚实报告不确定性」这个设计是否被用户接受。
> 选 C 说明措辞需要改（不是统计学问题，是文案问题）。

---

### Q7【单选，必答】你中途有没有过「不想再用了」的念头？

- A. 没有，用着挺顺
- B. 有过，但后来继续用了
- C. 有过，然后就基本没用了

> **报告用途**：留存与流失的最直接指标。
> 选 B、C 的人，一定要追问原因（Q9），这是产品最有价值的失败线索。

---

### Q8【单选，必答】你还会继续用吗？

- A. 会，而且会推荐给同学
- B. 会，但不会推荐
- C. 不确定
- D. 应该不会了

> **报告用途**：NPS（净推荐值）的简化版，可算出一个可比较的数字写进报告。
> 注意：样本小的时候只报分布，不要算出一个精确的百分比当结论。

---

### Q9【多行文本，选答】你觉得最该改进的地方是什么？

> 示例提示：可以吐槽任何地方，比如「每次都要手动选知识点太累了」
> 「图表看不懂」「手机上打字不方便」。越具体越好。

> **报告用途**：报告里「用户反馈与改进方向」一节的原始素材。
> **必须原文引用 2–3 条**（征得同意可匿名化），比你自己总结一百句都可信。

---

### Q10【多行文本，选答】有没有哪个瞬间觉得「这个功能挺有用」？

> 示例提示：比如「组卷抽到了我正好忘记的那道题」「看到掌握度只有 29% 那个数字有点被戳到」

> **报告用途**：验证你的三个创新点里，哪个真正被感知到了。
> 如果没人提到「遗忘曲线」或「加权组卷」，说明这些做得太隐晦，需要在界面上说出来。

## 三、建问卷时的几个设置建议

| 设置项 | 建议 | 原因 |
|---|---|---|
| 是否匿名 | **必须匿名** | 实名会让同学说客套话，数据不可信 |
| 是否显示结果 | **不显示** | 避免互相影响 |
| 是否限制一次 | 是（同一设备一次） | 防重复提交 |
| 是否收集微信昵称 | **不要** | 匿名才有真话 |
| 是否必答 | Q1–Q8 必答，Q9–Q10 选答 | 开放题必答会让人放弃 |
| 完成提示 | 「谢谢！有具体想吐槽的直接发我」 | 引导二次反馈 |

## 四、拿到链接后怎么填进产品

编辑 `js/config.js`：

```js
QT.config = {
  // 把下面的空字符串换成你的问卷链接
  FEEDBACK_URL: 'https://wj.qq.com/s2/xxxxxxx/xxxx/',

  SAMPLE_LIMIT: 12
};
```

然后三个命令上线：

```bash
cd "C:/Users/fa'r/Desktop/挑战杯/03-错题通"

# 1. 重新打包（离线包也要带上新链接）
node build/make-dist.js

# 2. 提交
git add -A
git commit -m "填入反馈问卷链接"

# 3. 推送（直连常失败，用代理单条命令内临时推）
HTTPS_PROXY=http://127.0.0.1:7890 git push origin main
```

**验证是否生效**（约 1 分钟后）：

```bash
# 直连即可，国内站不需要代理
curl -sS https://yvdaoyin-ux.github.io/cuotitong/js/config.js | grep FEEDBACK_URL
```

看到链接而不是 `FEEDBACK_URL: ''` 就成了。再去线上设置页确认按钮出现。

## 五、发出去之后怎么处理数据（写给报告用）

### 5.1 收齐后先做三件事

1. **剔除自己填的测试答卷**（你会先自己试一遍）
2. **按 Q1 分层**：只打开看了看 / 1–2 天 / 3–6 天 / 一周以上，分开统计
3. **与导出数据交叉验证**：让对方在设置页点「导出使用数据（JSON）」发你，
   核对 Q2（自报题数）与实际 `mistakeCount` 是否一致

### 5.2 报告里能写的 / 不能写的

| 能写 | 不能写 |
|---|---|
| 「N 位同学试用，其中 M 位使用超过一周」 | 「X% 的用户表示满意」（样本太小，不能算百分比当结论） |
| 「最常被提及的问题是知识点选择麻烦（K 人）」 | 「用户普遍认为功能强大」（"普遍"是编的） |
| 「反馈原文：'……'」 | 「回收有效问卷 N 份，满意度 4.5 分」 |
| 「N 人中有 M 人在一周后仍在使用」 | 「留存率达到 X%」（N 小于 30 时报比例没有统计意义） |

**核心原则**：样本十几个人时，**报绝对人数，不报百分比**。
「12 人里有 9 人用了一周以上」是事实；「留存率 75%」听起来像统计结论，实际没有意义。

### 5.3 如果试用人数很少（比如只有 3–5 人）

不要慌，也别注水。改成**案例式呈现**：

> 深度访谈 4 位同学（数学分析 2 人、高等数学 2 人），试用 7 天，
> 期间共录入 87 道错题、完成 12 次组卷练习。以下是其中 2 位的具体反馈……

这种写法的说服力**不低于**一个 20 人的粗糙问卷，而且不会被追问统计效力。

## 六、我提醒你的两件事

### 1. 别在问卷里写「帮我打分」

一旦出现打分，评委就会问「评分量表怎么设计的、信效度如何」。
你没做过量表设计，答不上来。只问行为和具体问题，问不出统计上的麻烦。

### 2. Q5 和 Q7 可能得到不好看的结果

如果多数人说「没看懂那个百分比」（Q5 选 D），或者「有过不想用的念头」（Q7 选 B/C），
**这是真实情况，必须写进报告**，并接一句「下一版会怎么改」。

评委见过太多只说优点的作品。**主动暴露问题并给出改进方案**，比全篇自夸显得可信得多。
这也是为什么问卷里我坚持要问这两道。
